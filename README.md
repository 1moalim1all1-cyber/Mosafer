# مسافر | Mosafer — Phase 1: إعداد المشروع

## الخطوات لتشغيل المشروع على جهازك

### 1. المتطلبات (مجانية بالكامل)
- Flutter SDK (أحدث نسخة Stable): https://flutter.dev
- Android Studio (لتشغيل الـ Emulator أو بناء الـ APK)
- حساب Firebase (مجاني): https://console.firebase.google.com
- حساب Cloudinary (مجاني بدون بطاقة): https://cloudinary.com

### 2. فك ضغط المشروع وتثبيت المكتبات
```bash
cd mosafer_app
flutter pub get
```

### 3. إعداد Firebase
```bash
# تثبيت أداة FlutterFire (مرة واحدة بس)
dart pub global activate flutterfire_cli

# ربط المشروع بـ Firebase (هيطلب منك تختار/تنشئ مشروع Firebase)
flutterfire configure
```
ده هيولّد ملف `lib/firebase_options.dart` تلقائيًا. بعد كده ارجع لملف `lib/main.dart`
وفعّل السطر ده اللي متعلّق (commented):
```dart
options: DefaultFirebaseOptions.currentPlatform,
```

**مهم:** لازم تفعّل خطة **Blaze** من إعدادات المشروع في Firebase Console عشان Cloud Functions
تشتغل لاحقًا. الخطة دي مش هتكلفك فلوس طول ما استخدامك تحت الحصة المجانية الشهرية —
راجع الشرح اللي اتفقنا عليه في المحادثة.

### 3.1 نشر Cloud Functions وقواعد Firestore (ضروري من Phase 7)
```bash
npm install -g firebase-tools   # مرة واحدة بس لو مش مثبتة
firebase login
firebase use --add              # اختار نفس مشروع Firebase اللي عملته فوق

cd functions
npm install
cd ..

firebase deploy --only firestore:rules,firestore:indexes,functions
```
راجع `functions/README.md` لتفاصيل أكتر وأمر تجربة الدوال محليًا على
Emulator قبل النشر الفعلي.

### 4. إعداد Cloudinary
1. سجّل حساب مجاني على cloudinary.com
2. من Settings → Upload → Add upload preset:
   - Signing Mode: **Unsigned**
   - سمّيه `mosafer_unsigned` (أو أي اسم وحدّثه في .env)
3. انسخ `.env.example` باسم `.env` واملأ:
```
CLOUDINARY_CLOUD_NAME=اسم_الحساب_بتاعك
CLOUDINARY_UPLOAD_PRESET=mosafer_unsigned
```

### 5. تفعيل ملفات الترجمة (l10n)
```bash
flutter gen-l10n
```
ده هيولّد `lib/l10n/generated/app_localizations.dart` تلقائيًا من ملفات `app_ar.arb` و `app_en.arb`.

### 6. تشغيل المشروع
```bash
flutter run
```

### 7. بناء APK للاختبار (زي ما طلبت)
**أسهل طريقة لو عندك مشاكل في تثبيت Flutter محليًا:** راجع
**`BUILD_VIA_GITHUB.md`** — بتبني الـ APK على سيرفرات GitHub المجانية
من غير ما تحتاج Flutter على جهازك خالص.

أو محليًا بسكريبت جاهز بيعمل كل الخطوات فوق بضغطة واحدة:
```bash
./build.sh
```
أو يدويًا:
```bash
flutter build apk --release
```
هتلاقي الملف في: `build/app/outputs/flutter-apk/app-release.apk`

بعد ما تثبته على جهاز حقيقي، راجع **`TESTING_CHECKLIST.md`** — قائمة اختبار
شاملة لكل تدفق في التطبيق (تسجيل، حجز، دفع، شات، إشعارات Push حقيقية...)
عشان تتأكد كل حاجة شغالة فعليًا مش بس بتفتح.

## هيكل المشروع

```
lib/
  core/

```

الأساسي. لحد ما نوصل هناك، المخاطرة محدودة لأن المشروع لسه في مرحلة الاختبار

### ✅ محلولة في Phase 7 — نقطتين أمنيتين/معماريتين (تاريخيًا)
1. **إنشاء الإشعارات بيحصل من تطبيق العميل مباشرة** (مش من سيرفر)، يعني
   لما السائق يقبل حجز، تطبيقه هو اللي بيكتب إشعار للراكب في Firestore. ده
   حل شغال 100% وظاهر فعليًا في شاشة الإشعارات، لكنه مش موثوق زي سيرفر
   مركزي (لو التطبيق قفل فجأة قبل ما يخلّص الكتابة، الإشعار ممكن ميتبعتش).
   الحل النهائي **Cloud Functions Triggers** (`onBookingCreated`,
   `onBookingConfirmed`) المخطط لهم من الأول في التحليل الأساسي، هيتفعّلوا
   في **Phase 7** ويحلّوا المشكلة دي نهائيًا.
2. **الإشعارات دلوقتي بتظهر جوه التطبيق بس (In-app)**، مش كـ Push حقيقي

   فعلي لجهاز تاني لازم يمر عبر Firebase Admin SDK (سيرفر)، ومستحيل ولا

   الـ Push الحقيقي هيشتغل من غير أي تعديل في تطبيق الموبايل نفسه.

## ما تم إنجازه في Phase 7 (Cloud Functions - النقلة الأمنية الكبرى)
هنا فعليًا اتقفلت كل الثغرات المؤقتة اللي وثّقناها بصراحة من Phase 4 لحد
Phase 6. مشروع Cloud Functions كامل (Node.js 20 + TypeScript) في مجلد
`functions/`، وده اللي اتغيّر جوهريًا:

- ✅ **`createBooking`**: كل منطق الحجز (فحص المقاعد، خصم المحفظة، إنشاء
  الحجز) بقى بيتنفذ **من السيرفر بصلاحيات Admin SDK كاملة**، مش من تطبيق
  الراكب. العميل بقى بس بينادي الدالة وياخد نتيجة جاهزة.
- ✅ **`respondToBooking`** و **`cancelBooking`**: نفس النقلة - قبول/رفض/إلغاء
  الحجز، استرداد المحفظة، إرجاع المقاعد، كله سيرفر بالكامل.
- ✅ **`markTripCompleted`**: دالة جديدة كل السائق بيقفل بيها رحلته، وبتحوّل
  فعليًا أرباح الحجوزات المدفوعة بالمحفظة (بعد خصم عمولة المنصة: 10% عادي،
  5% لـ"راجع فاضي" تشجيعًا للمعروض الرخيص) لمحفظة السائق - النقطة دي كانت
  فجوة حقيقية في Phase 5 (الفلوس كانت بتتخصم من الراكب ومتوصلش لحد).
- ✅ **`onBookingCreated`**, **`onBookingStatusChanged`**, **`onNewChatMessage`**:
  Firestore Triggers بتبعت إشعارات + **Push حقيقي على مستوى نظام التشغيل**
  تلقائيًا وموثوق 100%، مش من كود العميل زي Phase 6.
- ✅ **`scheduledTripReminder`**: تذكير تلقائي للركاب قبل الرحلة بساعة.
- ✅ **`approveDriver`/`rejectDriver`**: جاهزين لاستخدام لوحة الإدارة في
  Phase 9 من غير ما تحتاج تلمس Firestore مباشرة.
- ✅ **`firestore.rules` اتقفلت للنسخة النهائية الصارمة**: العميل بقى
  Read-Only تمامًا على `trips.availableSeats`, `wallets.balance`, و

## ما تم إنجازه في Phase 8 (المراجعة والتجهيز للبناء)
مش قادر أشغّل `flutter build apk` فعليًا من عندي (بيئتي مفيهاش اتصال بـ
`pub.dev` ولا خوادم تحميل Flutter SDK - نفس القيود اللي شرحتها من الأول
عن الشبكة)، فبدل ما أدّعي إني بنيت APK وهمي، عملت اللي فعلاً هيوفّر عليك

- ✅ **`build.sh`**: سكريبت بيتأكد من `.env` و`firebase_options.dart`
  و`flutterfire configure` قبل ما يبني، بدل ما تكتشف نقص في نص البناء

## ما تم إنجازه في Phase 9 (لوحة الإدارة الكاملة)
آخر جزء أساسي من التحليل الأول - لوحة إدارة حقيقية شغالة داخل نفس تطبيق
Flutter (تحت مسارات `/admin/*`)، مش موقع منفصل، عشان تفضل ملتزم بقرار
"APK أولاً" اللي اتفقنا عليه من البداية.

- ✅ **Dashboard**: إحصائيات حية (رحلات نشطة، سائقين بانتظار المراجعة،
  حجوزات اليوم، إجمالي المستخدمين) عبر Firestore Aggregation Queries
- ✅ **مراجعة السائقين**: طابور كامل + شاشة مراجعة تفصيلية بتعرض كل
  المستندات الخمسة وبيانات السيارة جنبًا لجنب، وقبول/رفض بينادي
  `approveDriver`/`rejectDriver` الجاهزين من Phase 7 (مش تعديل مباشر)
- ✅ **طلبات المحفظة**: اعتماد/رفض طلبات الإيداع والسحب عبر Cloud Function
  جديدة (`resolveWalletRequest`) بتعدّل الرصيد بصلاحيات سيرفر آمنة فقط
- ✅ **إدارة المحافظات وأنواع السيارات**: CRUD كامل (إضافة/تعديل/حذف/تفعيل)
  - و**الأهم**: الصفحة الرئيسية وشاشة إنشاء الرحلة بقوا **بيقروا المحافظات
  من Firestore فعليًا** بدل القائمة الثابتة، مع قائمة احتياطية تلقائية لو
  الأدمن لسه معملش أي تعديل (فالتطبيق يفضل شغال من أول تشغيل)
- ✅ **الكوبونات والعروض**: CRUD كامل (نسبة مئوية أو مبلغ ثابت، حد أقصى
  للاستخدام) - ملحوظة: التطبيق الفعلي للخصم على السعر وقت الحجز لسه مش
  متكامل في `createBooking`، ده تحسين إضافي سهل يتضاف بعدين لو حبيت
- ✅ **الإعدادات العامة**: نسب العمولة (عادي/راجع فاضي) قابلة للتعديل من
  غير كود، ووسائل التواصل وبريد الدعم
- ✅ **حماية كاملة على مستوى الراوتينج**: أي مسار `/admin/*` بيترفض
  تلقائيًا لغير الأدمن، بالإضافة لقواعد Firestore الموجودة من قبل

### ملاحظة صادقة عن نطاق Phase 9
من التحليل الأصلي، بعض البنود (سجلات النظام Audit Log، الصلاحيات متعددة
المستويات داخل الإدارة نفسها، النسخ الاحتياطي، التقارير التفصيلية) اتأجلت
عمدًا - مش لأنها مستحيلة، لكن لأنها إضافات فوق أساس شغال بالفعل، وبناء
أساس متين أهم من تغطية كل بند نظريًا. أي واحد فيهم جاهز يتضاف في مرحلة
لاحقة براحتك.

## ما تم إنجازه في Phase 10 (الشاشات الناقصة + إصلاح أمني)
- ✅ **المفضلة**: زرار قلب في تفاصيل الرحلة + شاشة مفضلة كاملة (`favoriteTrips`
  على وثيقة المستخدم، بعملية `arrayUnion`/`arrayRemove` آمنة لأنها بتعدّل
  بيانات المستخدم لنفسه بس)
- ✅ **التقييم بعد الرحلة**: نافذة تقييم بالنجوم قابلة لإعادة الاستخدام (الراكب
  يقيّم السائق من شاشة "رحلاتي"، والسائق يقيّم الراكب من شاشة إدارة الحجوزات)
  + Cloud Function جديدة (`onRatingCreated`) بتحسب `avgRating` من كل التقييمات
  الحقيقية المخزّنة في Firestore على السيرفر، مش من رقم بيتراكم في العميل
  (منعًا لأي تلاعب). `totalTrips` بقى بيتحدّث تلقائيًا في `markTripCompleted`
  لكل من السائق والركاب المؤكدين
- ✅ **شاشة "رحلاتي"**: كل حجوزات الراكب بحالتها الحية، إلغاء الحجز (بينادي
  `cancelBooking` الجاهزة من Phase 7)، وتقييم السائق بعد اكتمال الرحلة
- ✅ **الصفحات الثابتة**: من نحن، اتصل بنا، الأسئلة الشائعة (Accordion)،
  الشروط والأحكام، سياسة الخصوصية — محتوى Firestore حقيقي مع نص احتياطي
  جاهز من أول تشغيل، وروابط الشروط والخصوصية اتضافت في شاشة التسجيل
- ✅ **إصلاح أمني مهم**: قاعدة تحديث `users` في `firestore.rules` كانت بتسمح
  للمستخدم يعدّل **أي حقل في بياناته بما فيها `role` و`avgRating` و
  `trustScore`** - ثغرة حقيقية كانت ممكن تخلي أي مستخدم يخلي نفسه أدمن.
  اتقفلت بحيث المستخدم يعدّل بياناته الآمنة بس (الاسم، الصورة، اللغة،
  المفضلة، حالة التحقق، FCM Tokens)
